### 1. 변경 배경

현재 LFW 결과는 리팩터링 전 코드, SurvFace 결과는 1차 리팩터링 후 코드에서
생성되었다. 따라서 두 결과를 같은 구현으로 얻은 직접 비교 결과라고 주장하기
어렵다. 앞으로도 코드 수정과 데이터셋 교대 실험이 반복되므로 다음 문제를 먼저
해결해야 한다.

1. 논문에서 “왜 이 지표와 기준을 선택했는가”를 사전에 고정된 평가 계약으로
   방어할 수 있어야 한다.
2. LFW와 SurvFace가 같은 commit, 모델, 전처리, 압축 profile, 평가 정의를
   사용했다는 실행 증거가 필요하다.
3. 데이터셋별 순차 노트북은 디버깅·교육·수동 복구용 legacy로 보존하되,
   반복 실험은 한 공통 노트북에서 변수를 선택하고 실행할 수 있어야 한다.
4. 빠른 확인과 논문용 전체 실험을 임의의 의미가 다른 모드로 나누지 않고
   `quick`과 `full` 두 실행 등급으로만 관리해야 한다.
5. 현재 Grad-CAM 결과는 saliency와 압축 오차의 연관성을 보여 주지만, 검색
   성능 개선이나 압축 오류의 인과적 설명까지 검증한 결과는 아니다.

- **보완**: 위 단계의 정식 Python 함수를 호출하는 선택적 공통 orchestration

- **금지**: 공통 노트북 안에 연구 계산을 복사하거나, LFW 규칙을 SurvFace에
  강제로 적용하거나, 노트북 파일을 다른 노트북에서 `%run`으로 연결
- **책임 경계**: 계산·DB 쓰기·artifact 생성은 `.py`, 공통 노트북은 설정,

즉 구조는 다음과 같다.

```text
공통 실행 노트북
  -> 실행 계약 및 quick/full scope 검증
  -> dataset adapter 선택
  -> 공통 Python phase dispatcher
  -> LFW 또는 SurvFace protocol adapter
  -> RunStore/DB/artifact

데이터셋별 legacy 노트북
  -> 동일한 Python phase 함수를 단계별로 직접 호출
```

### 3. 고정 실행 등급

실행 등급은 `quick`, `full` 두 개만 사용한다. 둘 다 실제 이미지, 실제 등록
모델과 실제 평가 코드를 사용한다.

```python
QUICK_DATA_FRACTIONS = {
    "lfw": 0.10,
    "survface": 0.02,
}

FULL_DATA_FRACTION = 1.00
```

- `quick`
  - 목적: 코드·DB·artifact 흐름 확인, 경향 탐색, 실패를 저비용으로 발견
  - 표본: identity와 protocol role을 보존하는 결정적 표본 추출
  - 논문 최종 수치 사용: 금지
  - `paper_eligible`: `false`
- `full`
  - 목적: 논문에 사용할 전체 protocol 결과 생성
  - 표본: 반드시 `data_fraction=1.00`
  - `data_fraction != 1.00`이면 실행 전 중단
  - 논문 사용 가능 여부는 추가 재현성·계보 검증을 통과한 뒤 판정

현재 manifest와 seed 42 기준 예상 quick 규모는 다음과 같다. manifest가
변경되면 실행 시 다시 계산하여 plan에 기록한다.

| 데이터셋 | quick fraction | 예상 이미지 수 | 전체 이미지 수 |
|---|---:|---:|---:|
| LFW | 0.10 | 1,706 | 13,233 |
| SurvFace | 0.02 | 8,782 | 463,341 |

표본은 단순 선두 행 절단이 아니라 identity-aware, role-preserving 방식으로
선택한다. 동일 seed와 동일 manifest hash라면 같은 표본이어야 하며, 선택된
image ID 목록과 hash를 run에 저장한다. 특히 quick 결과의 낮은 FPIR은 표본 수가
부족하므로 결론 수치가 아니라 실행 확인용으로만 해석한다.

### 4. 논문 평가 계약 v1

#### 4.1 사전 고정 주 비교 profile

본문의 주 비교는 다음 네 profile로 고정한다.

1. `Origin-512`: 비압축 FP32 기준
2. `PCA-256`: 중간 압축률의 기존 주 비교점
3. `PCA-128`: 더 강한 차원 축소에서 성능·저장량 trade-off를 확인하는 추가점
4. `PQ-m128`: `origin_512`에 직접 학습한 `m=128`, `nbits=8` PQ

PCA 전체 차원과 PQ 전체 `m` sweep은 부록·민감도 분석에 유지한다. 본문 profile을
test 결과가 좋아 보이는 조합으로 사후 교체하지 않는다. 변경이 필요하면 별도의
평가 계약 버전과 변경 사유를 남기고 기존 결과와 섞지 않는다.

#### 4.2 PQ 검색 경로

- PQ 주 검색: exhaustive ADC
- IVF-PQ: 선택된 profile에 한한 시스템 효율 실험
- 금지: PQ code를 decode한 FP32 벡터의 cosine 검색을 ADC 성능으로 표기
- 필수 보고: codebook, `m`, `nbits`, code bytes, index bytes, 학습 표본 계보,
  search latency, recall/DIR/FPIR

현재 완료된 SurvFace PQ 산출물이 codec reconstruction만 수행하고 실제
`IndexPQ`/ADC 검색을 하지 않았다면, 그것은 PQ 검색 성능 근거가 아니다. 새
평가 계약의 PQ 결과는 별도 재실험이 필요하다.

#### 4.3 두 baseline의 병행

두 baseline은 서로 대체하지 않고 목적을 구분하여 모두 유지한다.

- Official baseline: 데이터셋 공식 evaluator와 공식 거리·template 규칙을
  가능한 한 그대로 재현하여 외부 타당성을 확인
- DB baseline: 정규화 임베딩, PostgreSQL/pgvector, cosine 기반 실제 저장·검색
  시스템을 평가

논문 표와 artifact에는 `baseline_family`를 반드시 기록한다. 공식 MATLAB
mean/Euclidean 수치와 DB normalized-mean/cosine 수치를 같은 열에서 동일
baseline처럼 비교하지 않는다.

#### 4.4 calibration과 threshold

- calibration enrollment size: 100명, 500명, 1,000명
- threshold 보고:
  - `frozen_origin`: Origin에서 정한 threshold를 압축 profile에 그대로 적용
  - `recalibrated`: 각 압축 profile의 허용된 calibration split에서 다시 산출
- test split로 threshold나 profile을 선택하지 않는다.
- calibration identity와 evaluation identity의 분리를 검증한다.
- threshold artifact에는 dataset, split, identity 수, seed, score definition,
  source profile, target FPIR, realized FPIR, manifest hash를 기록한다.

`frozen_origin`은 압축으로 인해 원래 의사결정이 얼마나 깨지는지 측정하고,
`recalibrated`는 허용된 재보정 후 회복 가능한 성능을 측정한다. 두 값의 목적이
다르므로 하나만 보고하지 않는다.

#### 4.5 FPIR과 주 지표

- 정식 보고 target: 30%, 20%, 10%, 1%, 0.1%
- 탐색적 target: 0.01%
- 0.01%는 non-mated 시행 수가 충분하고 신뢰구간을 함께 제시할 때만 정식
  주장 후보가 된다.
- 핵심 검색 지표: DIR@FPIR, FNIR/FPIR, rank-1 및 필요한 rank-k
- 압축 진단 지표: angular error, cosine score drift, rank flip,
  threshold crossing
- 효율 지표: vector/code/index bytes, query latency distribution, throughput,
  build/fit time

각 target에는 realized FPIR, 분모, 오탐 건수와 신뢰구간을 함께 기록한다.
target 값만 맞춘 것처럼 표기하지 않는다.

#### 4.6 template aggregation

- 주 baseline: mean
- ablation: quality-weighted mean

quality 정의, 정규화, 결측 처리, weight 범위는 calibration 전에 고정한다.
quality-weighted mean은 test 성능이 좋다는 이유만으로 주 baseline으로 승격하지
않는다.

### 5. 동일 코드 기반 비교 계약

앞으로 “LFW와 SurvFace를 비교했다”는 주장은 아래가 모두 같거나 명시적으로
차이를 설명할 때만 허용한다.

1. Git commit과 source snapshot hash
2. Python 환경 및 주요 dependency
3. `model_uid`, checkpoint hash, preprocessing contract
4. compression 구현과 profile 정의
5. metric/evaluation contract version
6. scope seed와 표본 manifest hash
7. DB schema/migration version

현재 legacy LFW 임베딩 경로는 InsightFace `buffalo_l` 계열을 사용할 수 있고,
현재 SurvFace 경로는 등록된 PyTorch ArcFace checkpoint를 사용한다. 이 model
identity 차이가 해소되기 전의 두 결과는 역사적·탐색적 결과로 보존하되, 새
계약의 직접 비교 표에는 사용하지 않는다. 논문용 비교에서는 두 데이터셋을 같은
등록 모델로 처음부터 다시 실행한다.

완료된 run은 수정하지 않는다. 코드 교정 후에는 새 run ID로 실행하고, 이전
run은 `superseded` 관계로만 연결한다.

### 6. 공통 노트북의 목표와 단계적 구현

목표 위치는 다음과 같다.

```text
notebooks/common/orchestration/00_batch_experiment_runner.ipynb
```

초기 구현은 다음 기능부터 제공한다.

1. dataset(`lfw`, `survface`)과 tier(`quick`, `full`) 선택
2. 고정 fraction 및 평가 계약 로드
3. manifest, 모델, config, CUDA, DB와 출력 경로 preflight
4. 실행 plan과 예상 표본 수 출력
5. `EXECUTE=False` 기본값
6. 구현된 canonical phase만 명시적으로 dispatch
7. 중단 후 같은 run을 재개할 수 있는 checkpoint/status 확인

아직 canonical Python phase로 분리되지 않은 legacy 셀을 노트북 JSON 실행이나
복사·붙여넣기로 우회하지 않는다. 해당 단계는 먼저 `.py` 함수로 추출하고
dataset별 legacy 노트북과 공통 노트북이 같은 함수를 호출하도록 교정한다.
공통 노트북은 phase coverage가 완성되기 전까지 `full pipeline implemented`라고
표기하지 않고, 미지원 단계를 fail-closed로 중단한다.

### 7. Grad-CAM의 현재 지위

현재 완료된 SurvFace 결과는 대규모 표본에서 saliency와 압축 오차 사이의
반복적인 약한∼중간 정도 연관성을 보여 주는 **보조 설명 결과**이다.

현재 결과만으로는 다음을 주장할 수 없다.

- saliency가 실제 모델 의사결정에 충실하다.
- saliency가 품질·pose·blur 같은 단순 변수보다 압축 실패를 더 잘 예측한다.
- saliency를 사용하면 고정 FPIR에서 DIR 또는 시스템 비용이 개선된다.
- 관찰된 상관관계가 압축 오류의 인과적 원인이다.

따라서 아래 승격 gate가 충족되기 전에는 Grad-CAM을 논문의 핵심 기여로
표기하지 않는다.

### 8. Grad-CAM 핵심 기여 승격 gate

#### G0. 설명 target과 단위 고정

- origin top-1 similarity target과 top-1/top-2 contrastive margin target을
  사전 정의하고 ablation한다.
- 등록 probe, unmated probe, gallery/template 역할을 분리한다.
- saliency가 입력 이미지, query-gallery pair, 또는 decision margin 중 무엇을
  설명하는지 명시한다.
- 랜드마크 region은 눈·코·입·얼굴 윤곽·배경을 포함하고, 좌표 실패·mask
  coverage·좌우 반전을 기록한다.

#### G1. Faithfulness 검증

saliency가 높은 영역을 가렸을 때 낮은 영역 또는 무작위 영역을 가린 것보다
target score/margin이 더 크게 변해야 한다.

- deletion/insertion 또는 동일 면적 occlusion
- high-saliency, low-saliency, random, landmark-matched random 비교
- identity, role, quality, 압축 profile을 층화한 실제 표본
- 1차 권장 규모: 데이터셋별 1,000∼5,000개 pair/query의 quick 실험
- 효과크기, bootstrap 신뢰구간, 반복 seed를 보고

G1을 통과하지 못하면 saliency를 모델 설명 변수로 사용하지 않는다.

#### G2. 교란과 다중 비교 통제

- 최소 통제 변수: 원본 score, top-1/top-2 margin, raw norm, 검출/정렬 품질,
  blur, pose, 밝기, 얼굴 크기, role, compression profile
- region 비율은 합이 1인 조성자료이므로 단순 독립 변수처럼 해석하지 않고
  CLR/ILR 또는 기준 region 대비 분석을 사용
- 여러 region·profile·outcome 비교에는 FDR 등 다중 비교 보정
- identity 단위 cluster bootstrap 또는 mixed-effects 구조 검토

기존 CSV로 가능한 재분석을 먼저 수행하고, 원본 Grad-CAM 재생성은 필요한
검증에만 제한한다.

#### G3. 독립 표본에서의 추가 예측력

identity-disjoint calibration/development/test 분할에서 다음 모델을 비교한다.

- cheap baseline: score, margin, reconstruction/angular error, raw norm, quality,
  pose, blur, profile
- proposed: cheap baseline + Grad-CAM region/faithfulness feature

예측 대상은 score drift, angular error, rank flip, threshold crossing,
false accept/false reject 또는 exact-fallback 필요 여부다. 회귀는 MAE/RMSE와
out-of-sample R², 분류는 AUROC뿐 아니라 AUPRC·calibration·결정 threshold
성능을 보고한다.

Grad-CAM 추가 후의 개선이 독립 test에서 반복되고 신뢰구간이 실질적 차이를
보여야 한다. 같은 데이터로 feature 선택과 평가를 동시에 하지 않는다.

#### G4. 고정 FPIR의 운영 개선

Grad-CAM을 실제 정책에 사용한 결과가 최소 하나의 실질적 효용을 보여야 한다.

- 같은 FPIR에서 DIR 증가
- 같은 DIR에서 exact-fallback 비율 또는 query 비용 감소
- 같은 latency/storage budget에서 오류 감소
- uncertainty rejection의 coverage-risk 개선

단순 상관계수 유의성만으로는 이 gate를 통과하지 못한다. 정책 비교에는
Grad-CAM 없는 cheap-feature 정책, random 정책, origin oracle 상한을 포함한다.

#### G5. 안정성과 일반화

- 좌우 반전, 작은 crop/정렬 변화, 반복 seed에 대한 region 안정성
- LFW와 SurvFace에서 방향·효과의 재현 여부
- 모델 간 일반화는 실제 등록·검증된 checkpoint가 있을 때만 추가
- 한 데이터셋 결과를 모든 얼굴 데이터에 일반화하지 않음

#### G6. 비용 타당성

- Grad-CAM backward, image decode, DB fetch, feature 생성까지 포함한 end-to-end
  latency와 처리량 측정
- 추가 artifact 저장량과 cold access 비용 측정
- 모든 query 실행과 uncertainty-gated 일부 query 실행을 비교
- GTX 1080 Ti 환경에서 얻은 실제 비용으로 효용 대비 비용을 판단

#### 승격 판정

Grad-CAM은 최소 G0∼G4와 G6을 통과하고, G5에서 데이터셋 간 한계가 명확히
기록될 때만 핵심 기여 후보로 승격한다. 일부 gate만 통과하면 보조 해석 또는
ablation으로 유지한다. faithfulness나 추가 예측력이 실패하면 핵심 기여에서
제외한다.

### 9. 예상 후속 실험 순서

| 순서 | 실험 | 새 Grad-CAM 필요 | 판정 목적 |
|---:|---|---|---|
| 1 | 기존 결과의 FDR·조성자료·교란 통제 재분석 | 아니오 | 현재 연관성의 과대해석 제거 |
| 2 | 1,000∼5,000개 층화 표본 faithfulness | 일부 | G1 통과 여부 |
| 3 | similarity와 contrastive target ablation | 일부 | 설명 target 확정 |
| 4 | 좌우 반전·작은 정렬 변화 안정성 | 일부 | G5 안정성 |
| 5 | cheap baseline 대 baseline+Grad-CAM 예측 | 기존+일부 | G3 추가 예측력 |
| 6 | 고정 FPIR selective fallback/rejection 정책 | 필요한 query만 | G4 운영 효용 |
| 7 | LFW/SurvFace 동일 코드·모델 full 재현 | 예 | 데이터셋 간 일반화 |
| 8 | end-to-end 비용·저장량 분석 | 예 | G6 비용 타당성 |

실험 1을 먼저 수행해 기존 artifact로 판단 가능한 한계를 확인한다. 비용이 큰

### 12. 검증 기준

1. quick/full 외 실행 등급을 허용하지 않는다.
2. fixed fraction이 plan과 run manifest에 동일하게 남는다.
3. full은 fraction 1.0이 아니면 실행되지 않는다.
4. 동일 manifest hash와 seed는 동일 ID 표본을 생성한다.
5. 공통 노트북과 legacy 노트북이 같은 `.py` 함수를 호출한다.
6. 미구현 phase는 건너뛰지 않고 실행 전에 명시적으로 중단한다.
7. LFW/SurvFace run manifest에 동일 contract version과 model UID가 남는다.
8. Origin/PCA/PQ 결과의 검색 경로와 threshold family가 구분된다.
9. notebook은 source에 output과 execution count를 저장하지 않는다.
10. Codex 검증은 실제 장시간 실험을 시작하지 않는다.

### 13. 미해결 위험

- LFW legacy extractor와 SurvFace 등록 PyTorch model의 parity 교정이 필요하다.
- data preparation, embedding, compression, official open-set의 일부 legacy 셀은
  아직 공통 canonical phase로 추출되지 않았을 수 있다.
- official baseline과 DB baseline의 template·거리 차이를 자동 검증할 계약
  테스트가 필요하다.
- PQ exhaustive ADC와 IVF-PQ는 현재 pgvector 경로와 별도 구현·artifact
  경계가 필요하다.
- quick 표본은 희귀 오류와 매우 낮은 FPIR을 안정적으로 추정하지 못한다.
- Grad-CAM gate의 최소 실질 효과크기와 허용 추가 latency는 pilot 결과 전에
  최종 수치로 고정할 수 없다. pilot 후 별도 버전으로 사전 고정한다.
- 로컬 실험 프로젝트이므로 GitHub Actions/CI 추가는 본 결정의 범위가 아니다.
