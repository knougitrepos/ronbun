## 1. 변경 배경

코드 리팩토링과 실험 개선을 반복하면서 한 임베딩 테이블에 여러 `run_uid`의
행이 함께 존재한다. 조회 코드가 `run_uid`를 정확히 제한하지 않으면 서로 다른
구현 시점의 데이터가 같은 실험처럼 섞일 수 있다.

2026-07-24 읽기 전용 점검 결과는 다음과 같다.

- `images`: 13,195행
- image/template embedding 테이블: `20260714-R004-16a5cbeb`,
  `20260715-R001-c305da87` 두 lineage가 공존
- `research_runs`: 0행
- 두 lineage의 로컬 `run_manifest.json`: 모두 `completed`

즉 현재 embedding lineage는 각 테이블의 문자열 `run_uid`와 로컬 manifest로만
식별되며 `research_runs` FK 레코드와 연결되어 있지 않다. 이를 이유로 조건 없는
테이블 전체 삭제를 제공하면 공유 image와 완료 기준선까지 손실될 위험이 있다.

## 2. 결정 내용

### 2.1 허용되는 삭제 범위

기본 삭제 단위는 **정확한 `run_uid` + 허용된 테이블 또는 테이블 그룹**이다.

- `image_embeddings`
  - `embedding_512/448/384/256/128`
  - `embedding_pq`
- `template_embeddings`
  - `template_embedding_512/448/384/256/128`
- `research_run_children`
  - `research_splits`
  - `research_templates`
  - `research_search_results`
  - `research_calibration_results`
- 개별 테이블도 위 allowlist 안에서만 선택할 수 있다.
- `research_runs` 부모 행은 직접 선택할 수 없다.
  `include_research_run_record=True`일 때 모든 FK 자식과 함께 마지막에 삭제한다.
- 과거 `run_uid IS NULL` 행은 nullable image embedding 테이블에 한해
  `legacy_null_run_uid`라는 별도 범위로만 처리한다.

다음 범위는 지원하지 않는다.

- 임의 SQL 또는 임의 `WHERE`
- 임의 테이블명
- 조건 없는 전체 테이블 삭제
- 공유 원본 `images` 삭제

### 2.2 실행 안전장치

삭제는 다음 순서를 모두 통과해야 한다.

```text
DB health 확인
  -> 전체 테이블 및 run_uid별 행 수 SELECT
  -> 정확한 범위의 행 수 미리보기
  -> DB 이름·사용자·상태·행 수 기반 plan digest 생성
  -> 완료 run 보호 확인
  -> 사용자가 확인 문자열을 설정
  -> 한 트랜잭션 시작
  -> PostgreSQL 대상 테이블 쓰기 잠금
  -> 같은 조건으로 행 수와 보호 상태 재확인
  -> FK 자식 -> 독립 embedding -> research_runs 부모 순서 DELETE
  -> 테이블별 삭제 수와 잔여 행 0건 검증
  -> 전부 일치할 때만 COMMIT
  -> 별도 감사 JSON 기록
```

- 노트북 기본값은 `CONNECT_TO_DATABASE=False`,
  `EXECUTE_DELETE=False`, 빈 `CONFIRMATION_TOKEN`이다.
- 미리보기 뒤 행 수, DB identity 또는 run 상태가 달라지면 전체 rollback한다.
- DB 또는 로컬 manifest에서 완료 상태를 확인하면
  `ALLOW_COMPLETED_RUN_DELETE=False`에서 확인 문자열 자체를 발급하지 않는다.
- 완료 run을 정말 폐기할 때만 보호를 명시적으로 해제하고 새 계획을 만든다.
- 삭제 성공 후 `runs/database_cleanup/`에 DB 비밀번호를 포함하지 않는 감사
  JSON을 기록할 수 있다.

## 5. 재실행 범위

1. 코드만 갱신했을 때 기존 실험과 임베딩을 다시 계산할 필요는 없다.
2. 삭제하려면 먼저 노트북을 읽기 전용 모드로 위에서 아래까지 실행한다.
3. 선택 범위 또는 완료 run override를 바꾸면 확인 문자열을 새로 발급받는다.
4. 실제 삭제 후 같은 노트북의 인벤토리를 다시 실행해 대상 행만 0인지 확인한다.
5. 삭제한 run을 다시 사용하려면 해당 run의 DB materialization 단계를 새
   lineage로 재실행한다. 완료 run artifact를 덮어쓰지 않는다.

## 6. 검증 기준과 결과

- allowlist 밖의 `images`, `research_runs` 직접 선택 및 임의 이름 거부
- 빈 scope와 조건 없는 삭제 거부
- 잘못된 확인 문자열 거부
- 미리보기 이후 행 수 변경 시 transaction rollback
- 선택한 run만 삭제하고 다른 run과 `images` 보존
- 완료 로컬 manifest가 있으면 기본 실행 차단
- `research_runs` 삭제 시 모든 FK 자식 자동 포함 및 자식 우선 삭제
- notebook JSON/schema, 코드 셀 문법, 빈 출력, 재시작 정책 검증
- 실제 PostgreSQL 읽기 전용 미리보기 검증:
  - `20260715-R001-c305da87`의 image/template 선택 범위 79,970행
  - 로컬 manifest `completed` 식별
  - 기본 설정에서 blocker 생성 및 확인 문자열 미발급

실제 PostgreSQL `DELETE`는 검증 항목에 포함하지 않았으며 이번 작업에서
실행하지 않았다.

## 7. 미해결 위험

1. **완료 run 삭제의 재현성 손실**
   - 감사 JSON은 삭제된 벡터 자체를 복구하지 않는다.
   - 필요한 기준선이면 삭제하지 말고 모든 조회를 `run_uid`로 고정한다.

2. **`research_runs`와 embedding lineage 불연결**
   - 현재 DB의 두 embedding run은 `research_runs`에 없다.
   - 후속 writer는 run 생성·status·embedding materialization의 연결을
     일관되게 기록해야 한다.

3. **외부 writer 동시 실행**
   - 실제 DELETE 트랜잭션은 대상 테이블 쓰기 잠금을 사용하지만 장시간
     materialization과 겹치면 대기 또는 실패할 수 있다.
   - 삭제는 실험 writer가 중지된 상태에서 수행한다.

4. **고아 `images`**
   - embedding 삭제 뒤 참조되지 않는 image 행이 남을 수 있다.
   - 원본 경로·hash provenance를 공유하므로 자동 정리하지 않는다.

5. **DB 백업 부재**
   - 도구는 선택 범위를 엄격히 검증하지만 row backup 기능은 제공하지 않는다.
   - 복구가 필요한 run은 PostgreSQL backup 또는 재생성 가능성을 먼저
     확인해야 한다.
