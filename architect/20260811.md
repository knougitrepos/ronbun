# 2026-08-11 Architecture Decisions

## 09:36 KST — 데이터셋 공통 population Grad-CAM 20,000장 상한

- 작성일: 2026-08-11 09:36 KST
- 상태: 구현됨, 단위·설정 회귀 검증됨, full GPU 실행 검증 대기
- 이전 결정과의 관계: `architect/20260728.md`의 LFW·SurvFace target 적격 표본 전수
  Grad-CAM 결정과 RFW-Custom 2,048장 상한을 폐기하고, 세 데이터셋에 동일한
  20,000장 상한을 적용한다. 전체 embedding·압축·검색 평가 범위는 유지한다.

### 변경 배경

AdaFace SurvFace full run에서 463,341장의 origin embedding 추출은 완료됐지만,
182,159장의 적격 표본 전체를 대상으로 하는 population Grad-CAM phase에서 커널이
종료됐다. backward Grad-CAM은 embedding·PCA/PQ·1:N 검색보다 표본당 비용과 메모리
부담이 크므로, 전체 데이터셋 평가 범위와 설명가능성 표본 범위를 분리할 필요가 있다.

### 결정 내용

- `gradcam.population.saliency_sample_cap`을 LFW, SurvFace, RFW-Custom 모두
  20,000으로 고정한다.
- 적격 표본 수가 20,000 이하이면 모든 적격 표본을 사용한다.
- 적격 표본 수가 상한을 초과하면 기존 deterministic sample-ID hash 선택을 사용한다.
  SurvFace는 `protocol_role`, RFW-Custom은 `rfw_group × protocol_role`, LFW는
  `split`을 층으로 보존한다.
- origin embedding, PCA/PQ characterization, open-set DIR/FPIR 평가는 선택된 full
  population 전체를 계속 사용한다. 20,000장 상한은 backward population Grad-CAM과
  그 saliency 파생 분석에만 적용한다.
- SurvFace의 별도 derived faithfulness 최대 2,048장 정책은 유지한다. 이는 최대
  20,000장의 저장된 Grad-CAM 표본 안에서 수행되는 더 작은 후속 평가다.

### 현재 구현과 목표 구조의 차이

- 구현·검증됨: canonical Step 4 YAML의 세 데이터셋 상한 통일, 상한 이하 적격 표본
  전수 유지 및 설정값 회귀 테스트.
- 검증 대기: 실제 GTX 1080 Ti에서 각 모델·데이터셋별 20,000장 상한 run 완료,
  실행시간·최대 RAM/VRAM·artifact 크기 측정.
- 미구현: Grad-CAM 결과의 실행 중 shard checkpoint와 phase 내부 resume. 현재 writer는
  phase 계산 완료 후 atomic publish하므로 중단 시 해당 phase는 다시 계산해야 한다.

### 데이터·모듈 흐름

```text
full selected population
  -> 전체 origin embedding
  -> 전체 PCA/PQ 및 open-set 검색 평가
  -> Grad-CAM 적격 판정
  -> min(적격 수, 20,000) 결정론적 층화 선택
  -> population Grad-CAM 및 saliency 분석
  -> SurvFace derived faithfulness 최대 2,048장
```

### 영향 범위

- 설정: `configs/experiments/step2_pytorch_gradcam.yaml`
- 선택 코드: `research/experiments/step4_datasets.py`의 기존 deterministic sampler
- 실행·검증: `research/experiments/step4_workflow.py`
- 테스트: `tests/research/test_step2_notebooks.py`,
  `tests/research/test_step4_datasets.py`
- 노트북: common batch runner가 canonical 설정으로 만드는 모든 새 plan/run
- DB: PostgreSQL/pgvector schema와 index에는 영향이 없다.
- artifact: 기존 completed/incomplete run은 변경하지 않으며 새 science config의 run과
  혼합하거나 같은 run으로 재개하지 않는다.

### 재실행 범위와 검증 기준

1. 변경 코드를 clean commit으로 고정하고 Jupyter kernel을 재시작한다.
2. 기존 20,000장 상한 이전 incomplete run을 자동 재개하지 않고 새 config/run으로
   실행한다. 완료된 origin embedding의 교차-run 재사용은 별도 SHA·config lineage
   계약을 구현·검증하기 전에는 허용하지 않는다.
3. phase manifest에서 `gradcam_selected <= 20000`, `heatmaps <= 20000`을 확인한다.
4. 적격 수가 20,000 미만인 데이터셋은 `gradcam_selected == eligible_rows`여야 한다.
5. 상한을 적용한 데이터셋은 동일 seed와 source manifest에서
   `saliency_selection_sha256`이 재현돼야 하며 지정된 protocol/group strata가 보존돼야
   한다.
6. 전체 population 수와 compression/retrieval 행 수는 Grad-CAM 상한 때문에 줄어들지
   않아야 한다.

### 미해결 위험

- 20,000장은 182,159장 전수보다 작지만 네 모델 전체 campaign에서는 여전히 상당한
  GPU 비용이다. 첫 실제 run에서 처리량과 메모리를 측정해야 한다.
- 실행 중 결과를 shard 단위로 publish하지 않으므로 kernel crash나 사용자 중단 시
  완료 전 Grad-CAM 배치를 복구할 수 없다.
- saliency 결론은 전체 데이터셋 전수 결과가 아니라 결정론적 층화표본 결과로
  보고해야 한다.

## 10:02 KST — 20,000장 상한 적용 보류 및 전수 Grad-CAM 재검증

- 작성일: 2026-08-11 10:02 KST
- 상태: 구현 설정 되돌림, 전수 GPU 실행 검증 대기
- 이전 결정과의 관계: 이 문서의 09:36 KST 공통 20,000장 상한 결정을 구현 전
  보류한다. 원인은 AdaFace SurvFace kernel crash이지만, 동일한 182,159장 전수
  Grad-CAM을 ArcFace가 정상 완료한 artifact가 있으므로 표본 수만을 원인으로
  단정하지 않는다.

### 결정 내용

- canonical config를 기존 전수 정책으로 복원한다: LFW와 SurvFace의
  `saliency_sample_cap=null`, RFW-Custom의 기존 2,048장 상한.
- 다음 AdaFace SurvFace run은 182,159장의 target-eligible sample 전체에 대해
  Grad-CAM을 수행한다.
- 같은 종류의 AdaFace kernel crash가 재현되면, crash log, CUDA device 상태,
  target-layer activation shape 및 peak memory를 먼저 보존·조사한 뒤에만
  20,000장 상한을 새 science config로 다시 도입한다.

### 재실행 범위와 검증 기준

1. 불완전 AdaFace SurvFace run은 새 full config와 호환되지 않으므로 삭제하고
   새 run ID로 시작한다.
2. ArcFace completed run은 immutable historical evidence로 보존한다.
3. AdaFace Phase 02는 `gradcam_selected=182159`와 `heatmaps=182159`를 기록해야
   하며, `COMPLETED`까지의 모든 phase manifest를 확인한다.
4. kernel crash가 발생하면 notebook traceback뿐 아니라 Windows/Jupyter/CUDA의
   native error evidence와 마지막 phase event를 보존한다.
