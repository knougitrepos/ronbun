  - detector 실행 provider와 로드 모듈 범위를 이번 문서로 구체화한다.

## 1. 변경 배경

aligned-crop materializer의 기본 provider가 `CPUExecutionProvider` 하나로
고정돼 있었다. 또한 InsightFace `buffalo_l`의 detection 외 모듈도
`FaceAnalysis.get`에서 얼굴마다 실행되어 전체 LFW 처리 시간이 불필요하게
길어졌고 사용자가 실행을 중단했다.

로컬 검증 환경은 GTX 1080 Ti, PyTorch `2.7.1+cu118`, CUDA runtime 11.8이며
ONNX Runtime 1.16.3에서 `CUDAExecutionProvider`를 사용할 수 있다.

## 2. 결정 내용

1. aligned crop의 provider 우선순위는 다음으로 고정한다.

   ```text
   CUDAExecutionProvider
     -> CPUExecutionProvider
   ```

2. CUDA를 primary provider로 요청했는데 설치 목록에 없거나 실제 detection
   session의 첫 provider가 CUDA가 아니면 전체 데이터 실행 전에 중단한다.
3. InsightFace에는 `allowed_modules=["detection"]`을 전달해 이미지별 추론은
   face detection과 5-point landmark 생성만 수행한다.
4. `ctx_id=0`만으로 GPU 사용을 판정하지 않고 실제 ONNX session provider를
   검사한다.
5. bundle manifest에는 요청 provider, 실제 provider와 detection-only 모듈
   경계를 기록한다.

## 3. 현재 구현과 목표 구조의 차이

| 항목 | 현재 상태 | 남은 조건 |
| --- | --- | --- |
| CUDA provider 설정 | 구현·단위 검증 | 전체 LFW 처리량 측정 |
| 조용한 CPU fallback 차단 | 구현·단위 검증 | CUDA 장애 상황 운영 점검 |
| detection-only 이미지별 추론 | 구현·실제 smoke 검증 | 13,233장 실패율 확인 |
| provider manifest 기록 | 구현·synthetic round-trip 검증 | 실제 bundle manifest 생성 |
| 전체 aligned bundle | 미실행 | 노트북 Run All 필요 |

## 4. 데이터·모듈 흐름

```text
LFW manifest
  -> InsightFace buffalo_l detection model only
  -> ONNX Runtime CUDAExecutionProvider
  -> bbox + 5-point landmark
  -> ArcFace 112x112 RGB alignment
  -> NPY + CSV indexes + JSON manifest
```

이미지 decode, source SHA-256, CSV/JSON 및 NPY 기록은 계속 CPU에서 수행한다.

## 6. 재실행 범위

1. 기존 aligned bundle이 없다면 노트북을 처음부터 실행한다.
2. 과거 CPU materializer로 만든 bundle이 있으면 provider와
   `materializer_version`이 다르므로 새 canonical bundle로 교체한다.
3. aligned bundle hash가 바뀌면 이를 입력으로 사용하는 미완료 Step 2 run은
   새 lineage에서 다시 시작한다.
4. 완료 run은 수정하지 않고 기존 입력 hash와 함께 보존한다.

## 7. 검증 기준과 결과

- CUDA 11.8 환경에서 ONNX detection session의 첫 provider가 CUDA
- `FaceAnalysis.models`에 detection만 유지
- 실제 LFW 이미지에서 얼굴 1개와 `(5, 2)` landmark 생성
- CUDA 미설치 및 CUDA session 비활성 시 fail-closed
- synthetic bundle manifest에 요청·실제 provider 기록
- notebook JSON, 코드 compile, 빈 output과 restart policy 유지

전체 LFW bundle, 처리 시간, GPU 사용률과 detection 실패율은 아직 검증하지
않았다.

## 8. 미해결 위험

1. InsightFace는 초기화 시 모델 파일을 순회하므로 시작 로그와 일회성 session
   생성 비용은 남지만, 이미지별 추론은 detection에 한정된다.
2. GTX 1080 Ti의 VRAM과 CUDA/cuDNN 호환성이 바뀌면 session 생성 단계에서
   실패할 수 있다.
3. GPU 가속 후에도 이미지 decode와 파일 hash 때문에 GPU 사용률은 간헐적으로
   낮아질 수 있다.
4. detector 또는 provider 변경은 crop hash를 바꿀 수 있으므로 서로 다른
   bundle을 같은 lineage로 합치면 안 된다.

## 변경 배경과 결정

LFW DB run 설정은 과거 `[448, 384, 256, 128]`을 사용했지만 새 Step 1
압축 특성 실험은 `[384, 256, 128, 64, 32]`를 사용하여 같은 단계 안에서
프로파일과 compressor artifact가 충돌했다.

새 활성 PCA family는 원본 512D에서 각각 독립적으로 학습하는
`pca_384`, `pca_256`, `pca_128`, `pca_64`, `pca_32`로 통일한다.
`pca_448`은 새 run에서 생성하지 않고 과거 run과 artifact를 읽기 위한
legacy 프로파일과 DB 테이블로만 보존한다.

## 구현과 데이터 흐름

```text
LFW development origin-512
  -> PCA 384/256/128/64/32 독립 학습
  -> compressor artifact 고정
  -> image embedding_384/256/128/64/32 materialization
  -> template_embedding_384/256/128/64/32 materialization
  -> 차원별 exact/HNSW 검색 및 압축 특성 평가
```

`embedding_64`, `embedding_32`, `template_embedding_64`,
`template_embedding_32` 모델을 추가하고 `Base.metadata.create_all`과
`ensure_vector_indexes`가 실제 PostgreSQL에서 테이블 및 cosine HNSW
인덱스를 생성하도록 연결했다. cleanup/reset allowlist에도 네 테이블을
포함했다.
