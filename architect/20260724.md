## 2. 결정 내용

### 2.1 허용되는 삭제 범위

기본 삭제 단위는 **정확한 `run_uid` + 허용된 테이블 또는 테이블 그룹**이다.

- `image_embeddings`
  - `embedding_512/448/384/256/128`
  - `embedding_pq`
- `template_embeddings`
  - `template_embedding_512/448/384/256/128`
- `research_run_children`
  - `research_splits`
  - `research_templates`
  - `research_search_results`
  - `research_calibration_results`
- 개별 테이블도 위 allowlist 안에서만 선택할 수 있다.
- `research_runs` 부모 행은 직접 선택할 수 없다.
  `include_research_run_record=True`일 때 모든 FK 자식과 함께 마지막에 삭제한다.
- 과거 `run_uid IS NULL` 행은 nullable image embedding 테이블에 한해
  `legacy_null_run_uid`라는 별도 범위로만 처리한다.

다음 범위는 지원하지 않는다.

- 임의 SQL 또는 임의 `WHERE`
- 임의 테이블명
- 조건 없는 전체 테이블 삭제
- 공유 원본 `images` 삭제

### 2.2 실행 안전장치

삭제는 다음 순서를 모두 통과해야 한다.

```text
DB health 확인
  -> 전체 테이블 및 run_uid별 행 수 SELECT
  -> 정확한 범위의 행 수 미리보기
  -> DB 이름·사용자·상태·행 수 기반 plan digest 생성
  -> 완료 run 보호 확인
  -> 사용자가 확인 문자열을 설정
  -> 한 트랜잭션 시작
  -> PostgreSQL 대상 테이블 쓰기 잠금
  -> 같은 조건으로 행 수와 보호 상태 재확인
  -> FK 자식 -> 독립 embedding -> research_runs 부모 순서 DELETE
  -> 테이블별 삭제 수와 잔여 행 0건 검증
  -> 전부 일치할 때만 COMMIT
  -> 별도 감사 JSON 기록
```

- 노트북 기본값은 `CONNECT_TO_DATABASE=False`,
  `EXECUTE_DELETE=False`, 빈 `CONFIRMATION_TOKEN`이다.
- 미리보기 뒤 행 수, DB identity 또는 run 상태가 달라지면 전체 rollback한다.
- DB 또는 로컬 manifest에서 완료 상태를 확인하면
  `ALLOW_COMPLETED_RUN_DELETE=False`에서 확인 문자열 자체를 발급하지 않는다.
- 완료 run을 정말 폐기할 때만 보호를 명시적으로 해제하고 새 계획을 만든다.
- 삭제 성공 후 `runs/database_cleanup/`에 DB 비밀번호를 포함하지 않는 감사
  JSON을 기록할 수 있다.

따라서 Grad-CAM을 오류 사례의 사후 부가기능이 아니라 원본 이미지별 분석

전체 관계 분석을 마친 뒤 그림을 만드는 데만 사용한다.

## 2. 결정 내용

### 2.1 분석 단위와 두 번의 forward

선택 표본 \(i\)의 원본 unit embedding을 \(e_i\), 같은 split·identity 안의
다른 표본 집합을 \(I_i\)라고 한다.

\[
t_i =
\operatorname{normalize}\left(\sum_{j \in I_i,\;j\ne i} e_j\right),
\qquad
S_i=e_i^\mathsf{T}\operatorname{stopgrad}(t_i)
\]

실제 계산은 다음 두 pass로 나눈다.

1. **Pass A**
   - 선택된 모든 이미지의 raw 512D, raw norm, unit embedding을 추출한다.
   - 전체 embedding이 준비된 뒤 자기 자신을 제외한 동일인 template을 만든다.
2. **Pass B**
   - LOO target이 있는 모든 이미지에서 같은 모델·전처리·target layer로
     forward/backward를 수행한다.
   - Pass B embedding과 Pass A embedding의 cosine이 설정 기준
     `0.99999` 이상인지 확인한다.

개념적으로는 한 origin-feature stage지만 LOO template이 다른 이미지의
embedding을 필요로 하므로 물리적으로 한 번의 forward로 끝낼 수 없다.

### 2.2 “모든 이미지”의 정확한 의미

- 원본 embedding과 sample record: **모든 선택 이미지**
- identity LOO Grad-CAM: **target-eligible 선택 이미지**
- singleton 또는 identity 누락:
  - embedding과 행은 유지
  - `saliency_target_eligible=False`
  - `singleton_identity`, `missing_identity` 등의 사유 기록
  - 다른 target으로 조용히 대체하지 않음

현재 LFW full manifest의 관측치는 다음과 같다.

| 항목 | 이미지 수 | 비율 |
| --- | ---: | ---: |
| 전체 | 13,233 | 100% |
| 동일인 LOO 가능 | 9,164 | 69.25% |
| singleton identity | 4,069 | 30.75% |

따라서 “전체 이미지 Grad-CAM 100%”는 현재 목표 정의로는 성립하지 않는다.
정확한 표현은 **전체 이미지 embedding 100% + 전체 LOO-eligible 이미지
Grad-CAM**이다. 각 dev/real 선택 범위에서 실제 coverage를 다시 기록한다.

### 2.3 저장 특징

전체 선택 표본의 feature table에는 다음을 둔다.

- provenance:
  `extraction_uid`, `dataset_id`, `sample_id`, `identity_id`, `model_uid`,
  `origin_embedding_artifact_uid`, `saliency_spec_uid`
- 원본:
  raw embedding norm, identity-template cosine, LOO eligibility/status
- Grad-CAM:
  raw CAM, ReLU CAM, normalized native-resolution heatmap, channel weight,
  gradient L2, CAM mass, valid-map flag
- 공간 요약:
  4사분면 집중도, entropy, 중심 x/y, spread, 좌우 비대칭,
  maximum region concentration
- mask가 있을 때만:
  눈·코·입·볼·턱·얼굴 외부 집중도
- faithfulness:
  high-saliency, low-saliency, sample-id seeded random occlusion score drop

전체 activation과 gradient는 저장량이 크므로 기본 artifact에 영구 저장하지
않는다. native CAM·channel weight·Pass B embedding은 shard로 저장하고 full
intermediate tensor는 명시적인 debug subset에서만 허용한다.

5-point landmark만으로 볼·턱·얼굴 외부 mask를 추정하지 않는다. 검증된
detector topology의 dense landmark 또는 face polygon이 없으면 해당 열은
결측으로 유지한다.

### 2.4 압축과 결합

Grad-CAM 특징은 embedding에 이어 붙이지 않는다. 동일한 원본 512D만 다음
독립 실험군에 입력한다.

- PCA-only: 384/256/128/64/32D
- PQ-only: 원본 512D에 직접 적용
- PCA→PQ 연쇄: 제외
- exact origin fallback: 제외

결합 키와 lineage는 다음과 같다.

```text
extraction_uid + dataset_id + sample_id + model_uid
origin_embedding_artifact_uid 일치
```

embedding distortion은 전체 이미지에 존재할 수 있지만 rank·threshold 변화는
open-set protocol query subset에만 존재할 수 있다. 따라서 retrieval
availability를 별도 열로 기록하며 없는 행을 임의 값으로 채우지 않는다.
상관은 모델·압축 family·profile별로 분리하고 identity-cluster bootstrap을
사용한다.

### 2.5 노트북 순서

```text
00 source/scope/alignment/model freeze
  -> 01 Pass A origin embedding + LOO template
  -> 02 Pass B population Grad-CAM
  -> 03 coverage/spatial/faithfulness validation
  -> 04 same-origin PCA/PQ quantitative artifact validation
  -> 05 strict population join + profile-specific association
  -> 06 representative case visualization only
```

06은 저장된 heatmap을 읽기만 하며 Grad-CAM을 재생성하지 않는다.

6. **전체 데이터 계산 비용**
   - Grad-CAM과 7회의 faithfulness forward

     줄인다. 압축 결과 기반 표본 축소로 연구 질문을 다시 바꾸지 않는다.

7. **SurvFace 적용 한계**
   - official unmated probe는 실제 identity label이 없으므로 identity LOO
     target을 만들 수 없다.
   - 다른 target을 도입하면 별도 연구 조건과 `saliency_spec_uid`로 분리하며
     LFW LOO 통계에 섞지 않는다.

8. **정량 runner 부재**
   - 현재 04는 외부 runner 산출물의 provenance를 검사할 뿐 PCA/PQ를 fit하지
     않는다.
   - runner가 구현·검증되기 전에는 end-to-end Step 2 완료로 표시하지 않는다.

9. **높은 동일인 cosine에서의 gradient 소실**
   - leave-one-out이어도 query와 template이 거의 같으면 cosine gradient와
     CAM mass가 매우 작거나 heatmap이 무효가 될 수 있다.

## 1. 변경 배경

한 실험 run은 PostgreSQL에 저장된 embedding·template·검색 결과만으로
구성되지 않는다. 같은 `run_uid`에 연결된 임베딩 전처리와 추출 shard, PCA/PQ
model·codebook, Grad-CAM/LOO, 평가 표·그림·로그와 active pointer가 로컬에도
존재한다. DB 행만 삭제하면 이전 구현의 로컬 artifact가 새 DB materialization과
결합될 수 있고, 로컬 결과만 지우면 DB의 오래된 vector가 재사용될 수 있다.

따라서 일반적인 리팩토링 및 재실행 전 정리 단위를 테이블별 DELETE가 아니라
**exact `run_uid`가 소유한 DB와 로컬 lineage 전체**로 확장한다. 단, 공유
데이터와 모델을 run 소유로 오인하지 않도록 자동 선택 범위는 증명 가능한
owner에 한정한다.

## 2. 결정 내용

### 2.1 두 모드의 책임

### 2.3 complete reset의 로컬 범위

   - LOO template, Grad-CAM heatmap·feature·faithfulness
   - 평가 표, 그림, 로그, phase/attempt manifest
2. `results/**/result_manifest.json`이 exact `run_uid`를 가리키는 결과 bundle
3. JSON의 `run_id`가 exact `run_uid`와 일치하는 `active_run.json`

과거 D 드라이브 절대경로가 pointer나 manifest에 남아 있더라도 그 경로를
따라가지 않는다. 현재 `PROJECT_ROOT` 아래를 직접 탐색하고 JSON의 exact owner

로컬 대상은 영구 삭제하지 않는다. 다음 위치로 상대 경로를 보존해 이동한다.

```text

```

격리 payload와 감사 JSON은 reset 대상에서 다시 재귀 선택하지 않는다.

### 2.5 보호 override

세 보호 조건은 서로 대체하지 않으며 각각 plan digest에 포함한다.

- `ALLOW_COMPLETED_RUN_RESET`
  - DB status 또는 로컬 manifest가 완료 상태인 run을 폐기할 때 필요하다.
- `ALLOW_PROMOTED_RESULTS_RESET`
  - `results/paper` 등 논문용으로 승격된 result bundle이 대상일 때 필요하다.
- `ALLOW_UNVERIFIED_LINEAGE_RESET`
  - DB 행은 있지만 owner manifest가 없거나 DB·로컬 lineage가 불완전한
    orphan run을 처리할 때 필요하다.

override를 바꾸면 기존 확인 문자열은 폐기하고 미리보기부터 다시 수행한다.
이는 보호를 해제할 권한일 뿐 보존 대상이나 임의 경로 allowlist를 넓히지 않는다.

### 2.6 transaction과 격리 순서

```text
exact RUN_UID 입력
  -> DB·runs·results·active pointer 읽기 전용 inventory
  -> exact owner와 항상 보존할 대상 판정
  -> 완료/promoted/unverified blocker 판정
  -> DB identity·행 수·경로·파일 수·byte·override의 plan digest 생성
  -> 사용자가 전체 확인 문자열 입력
  -> PostgreSQL transaction과 대상 테이블 lock
  -> DB 행 수·상태와 로컬 대상 재검증
  -> FK-safe DB DELETE 수행, 아직 commit하지 않음
  -> 로컬 대상 quarantine move callback
       실패: 이동 완료분 원위치 복원 + DB rollback
       성공: DB commit
  -> DB 잔여 행·pointer·격리 payload 검증
  -> 비밀정보 없는 cleanup 감사 JSON 기록
```

PostgreSQL과 파일시스템은 하나의 원자적 transaction을 공유하지 않는다.
정상적인 callback 예외는 rollback과 복원으로 처리하지만, 파일 이동과 DB
commit 사이에 프로세스·OS가 강제 종료되는 crash window 자체를 제거할 수는
없다. 실제 reset은 writer를 중지한 상태에서 수행하고, 감사·quarantine과 DB
상태를 재점검해야 한다.
