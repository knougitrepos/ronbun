### 변경 배경

SurvFace full 조건의 Phase 04는 182,159 probe와 250 threshold/search 조건을 결합하여
45,539,750 logical retrieval 행을 만들었다. 기존 구현은 모든 조건 DataFrame을 list에
보존한 뒤 `pd.concat`하고, top-k tuple 문자열과 threshold-invariant search 결과를 반복한
약 171.48 GiB CSV를 기록했다. Phase 05는 여기서 19개 saliency feature가 반복된 약
9.14 GiB Parquet projection을 다시 전체 `pd.read_parquet`하여 process commit 약 94.8 GiB,
physical RAM 약 95%, 단일 logical core 중심 사용 상태를 만들었다.

이 상태는 계산량의 필연적 최대 사용이 아니라 flat artifact와 전체 materialization 때문에
생긴 구조적 병목이었다. B=500, 다섯 FPIR, 모든 score-space 및 saliency metric을 줄이지 않고도
저장 중복과 동시에 메모리에 존재하는 group 수를 제한할 수 있다.

### 결정 내용

1. Phase 04의 retrieval 결과는 조건 batch가 생성되는 즉시
   `research/evaluation/retrieval_ledger.py`의 atomic writer로 전달한다.
   `collect_retrieval_metrics=False`인 canonical workflow에서는 전체 `retrieval_frames` list와
   마지막 `pd.concat`을 만들지 않는다. 기존 Python API의 기본값은 `True`로 유지하여 소규모
   호출자와 테스트 호환성을 보존한다.
2. normalized ledger는 다음 세 층으로 나눈다.
   - `core`: query × compression profile × search mode의 threshold-invariant search/score 행
   - `decisions`: `core_row_id` × target FPIR × threshold policy의 좁은 accept/event 행
   - `topk_detail`: full-retention 실행에서만 보존하는 Arrow list형 top-k 상세 행
3. `results_only` 실행은 결론 계산에 불필요한 6개 top-k 상세 열을 명시적으로 생략한다.
   `full` 실행은 이를 별도 detail table에 한 번만 보존한다. 두 모드 모두 manifest에 logical
   row 수, condition/decision 수, 사용 가능·생략 열, lineage, 각 Parquet의 byte 수와 SHA-256을
   기록하며 directory 단위로 atomic publish한다.
4. 동일 core가 여러 FPIR/policy에서 달라지면 writer가 content digest 불일치로 fail-close한다.
   reader는 byte 수와 SHA-256을 검증하고 CSV/Parquet/normalized ledger를 같은 bounded iterator
   인터페이스로 복원한다. 완료된 legacy CSV는 읽을 수 있지만 새 canonical run은 만들지 않는다.
5. `_summarize`와 RFW-Custom demographic summary는 각 retrieval batch에서 bounded accumulator로
   계산한다. full per-query frame을 수집하지 않아도 기존 Wilson/paired-delta/count 계약과 같은
   compact summary를 생성한다.
6. Phase 05 retrieval projection은 19개 saliency feature를 45.5M행에 반복하지 않는다.
   saliency lookup은 probe별 한 번만 Parquet에 기록하고, retrieval metric은 다음 base condition으로
   partition한다: dataset, model, family, profile, search mode, protocol, threshold/evaluation split,
   target FPIR. policy와 mated status는 같은 shard에 두어 paired-policy 검증이 완결되게 한다.
7. 각 shard만 saliency lookup과 결합하여 기존 네 분석을 모두 수행한다.
   - retrieval saliency association
   - threshold instability association
   - frozen 대 recalibrated event 비교
   - frozen 대 recalibrated saliency-rho 비교
8. 기본 worker는 4, 최대 in-flight partition은 8로 제한한다. 각 child process의 BLAS/OpenMP
   thread 수를 1로 제한하여 nested oversubscription을 막는다. bootstrap seed는 기존 group key와
   pair key에 의존하므로 partition 완료 순서나 worker 수가 수치에 영향을 주지 않는다.
9. B=500, bootstrap unit `identity_id`, weighted-rerank algorithm, saliency feature/metric,
   다섯 FPIR 및 ADC/SDC의 `recalibrated_compressed` 전용 score-space 규칙은 변경하지 않는다.
   통계량을 줄이는 cap, FPIR 축소 또는 bootstrap 축소는 이번 최적화에 포함하지 않는다.
10. Phase 05 manifest에는 partition algorithm version, worker/in-flight 제한, 기존 science algorithm
    version, seed와 네 구현 source SHA를 기록한다. cross-dataset loader는 새 fingerprint를 검증하고
    legacy 세-source fingerprint도 완료 artifact 호환 경로로 유지한다.
11. notebook의 `RUN_SEARCH_SPACE_REFRESH=True` 후처리는 새 Phase 04 ledger와 multi-target
    diagnostics를 직접 재사용한다. 새 run에서 PCA/PQ 검색을 다시 수행하거나 45.5M행을 다시
    concat하지 않는다. legacy run에 ledger가 없을 때의 refresh도 임시 normalized ledger로
    streaming하여 전체 retrieval DataFrame 수집을 피한다.

### 데이터·모듈 흐름

```text
condition별 retrieval comparison DataFrame
  -> bounded summary accumulator
  -> normalized retrieval ledger staging
       core/*.parquet             (search 결과 1회)
       decisions/*.parquet        (FPIR/policy별 좁은 행)
       topk_detail/*.parquet      (full 모드만)
       manifest.json + bytes/SHA
  -> directory atomic publish

Phase 05
  saliency_features (probe별 1회)
  + retrieval ledger bounded iterator
    -> threshold metric derivation + strict lineage/key 검증
    -> base-condition Parquet shards
    -> 최대 4 process / 8 in-flight
       각 worker: shard 1개 + saliency lookup -> 기존 exact association 함수
    -> canonical sort/merge
    -> compact association CSV 5종 + representative candidates
    -> 성공 후에만 canonical output publish
```

### 미해결 위험

1. 실제 SurvFace 45,539,750행에서 peak RAM, ledger byte 수, Phase 04/05 wall time과 평균 CPU는
   아직 측정하지 않았다. 구조상 동시 resident data는 전체 45.5M행이 아니라 core condition 또는
   association shard 수로 제한되지만, 최종 수치는 첫 full run의 telemetry로 확정해야 한다.
2. 기본 4 worker는 i5-10600K 6C/12T와 64 GiB RAM에 맞춘 보수적 값이다. 실제 shard 크기와
   pagefile이 안정적일 때만 5~6 worker를 별도 config/run으로 비교한다.
3. Phase 05 association 결과는 중간 partition별 durable checkpoint를 아직 남기지 않는다.
   kernel 중단 시 atomic compact output은 오염되지 않지만 해당 Phase 05 attempt 계산은 다시 한다.
4. full-retention mode는 top-k 상세를 보존하므로 results-only보다 디스크와 reader memory가 크다.
   논문 결론 생성 campaign은 현재처럼 results-only를 우선하고, 상세 감사가 필요한 별도 run만
   full을 선택한다.
5. manifest는 각 Parquet SHA를 고정하지만 directory 자체는 Git 추적 대상이 아니다. 완료 run
   보존/이동 전에는 기존 retention manifest와 독립 backup 정책을 적용해야 한다.
