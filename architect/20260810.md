# 2026-08-10 Architecture Decisions

## 03:32 KST — EdgeFace Grad-CAM 7×7 공통 격자 전환

- 작성일: 2026-08-10 03:32 KST
- 상태: 구현됨, 실제 체크포인트 smoke 검증됨, 전체 데이터셋 재실행 미완료

### 변경 배경

2026-08-09 기록은 EdgeFace의 Grad-CAM target layer를
`model.stages.3.blocks.2.convs.2`로 지정했다. 실제 EdgeFace-XS checkpoint에서 이
계층의 출력은 3×3이었다. SurvFace 전체 실행의 landmark face mask를 3×3으로
내리는 과정에서 유효한 원본 face mask 한 건이 완전히 사라져 Phase 02가
fail-closed로 중단되었다. 기존 ArcFace, AdaFace, MagFace saliency artifact는 모두
7×7이므로 3×3만을 위한 별도 mask 보정은 모델 간 비교 조건과 코드 경로를
불필요하게 분기한다.

### 결정 내용

- 2026-08-09의 EdgeFace target-layer 선택만 폐기하고, checkpoint·전처리·512D
  embedding 계약은 유지한다.
- EdgeFace target layer는 가장 깊은 7×7 convolution인
  `model.stages.2.blocks.8.convs.1`로 변경한다.
- 공통 Grad-CAM 공간 계약을 `expected_heatmap_size: [7, 7]`로 명시한다.
- smoke validation은 선택 계층의 실제 `[B,C,H,W]` 출력을 hook으로 확인하고,
  공간 크기가 7×7이 아니면 실행 전에 중단한다.
- population Grad-CAM도 첫 batch에서 실제 heatmap 크기를 다시 확인해 잘못된
  registry/config 조합을 fail-closed로 막는다.
- `model_uid`는 checkpoint·전처리 identity이므로 target-layer 변경만으로 바꾸지
  않는다. 대신 같은 `model_uid`의 분석 target 개정은 전체 ModelSpec digest를
  붙인 별도 immutable registry 파일로 보존하며, profile 선택 시 target layer까지
  일치시킨다.

### 현재 구현과 목표 구조의 차이

- 변경 전: EdgeFace만 3×3, 나머지 세 모델은 7×7이며 mask resize가 native CAM
  크기에 따라 달라졌다.
- 변경 후: 네 모델 모두 7×7 saliency grid를 사용하고 공통 mask·집계 경로를
  유지한다.
- 아직 남은 차이: 서로 다른 backbone의 7×7 계층은 의미적 깊이와 receptive
  field가 완전히 동일하지 않다. 이번 결정은 공간 해상도 통일이며 계층 의미의
  인과적 동등성을 주장하지 않는다.

### 데이터·모듈 흐름

`step2_pytorch_gradcam.yaml profile` → `ModelSpec target_layer` → profile-aware
immutable registry 선택 → model smoke의 target output 7×7 검증 → run config/source
freeze → population Grad-CAM 첫 batch 7×7 검증 → 7×7 landmark region mask slice →
saliency feature 및 compression join.

### 영향 범위

- 설정: `configs/experiments/step2_pytorch_gradcam.yaml`
- registry/선택: `research/embeddings/manifests.py`
- 공통 준비/smoke: `research/experiments/pipeline_runner.py`
- Step 4 실행: `research/experiments/step4_workflow.py`
- Grad-CAM 추출: `research/explainability/gradcam/extraction.py`
- 노트북: `notebooks/common/model_preparation/*`,
  `notebooks/common/orchestration/00_batch_experiment_runner.ipynb`
- artifact: 기존 3×3 EdgeFace saliency 조건과 새 7×7 조건은 혼합하거나 재사용하지
  않는다. `saliency_spec_uid`에는 target layer가 포함되어 서로 구분된다.

### 재실행 범위

- 기존 ArcFace/AdaFace/MagFace 완료 run은 target과 7×7 계약이 바뀌지 않으므로
  이 결정만을 이유로 무효화하지 않는다.
- 실패한 EdgeFace SurvFace run의 Phase 01 embedding은 checkpoint 관점에서는
  동일하지만, frozen run config가 이전 target을 가리키므로 새 7×7 실험으로
  재개하지 않는다.
- EdgeFace는 새 ModelSpec registry/smoke를 만든 뒤 dataset별 새 run을 Phase 00부터
  시작한다. 이전 incomplete run은 삭제하지 않고 보존하며, active-run 선택은
  사용자가 명시적으로 정리하거나 교체해야 한다.

### 검증 근거 및 기준

- 공식 EdgeFace-XS gamma=0.6 checkpoint, CUDA, 고정 smoke 이미지 8장:
  - 새 `model.stages.2.blocks.8.convs.1`: heatmap `(8,7,7)`, 유효 8/8,
    gradient L2 범위 약 4.409–9.928.
  - 이전 `model.stages.3.blocks.2.convs.2`: heatmap `(8,3,3)`, 유효 5/8.
- unit/integration 기준:
  - 같은 checkpoint/model_uid에서 서로 다른 target manifest를 immutable하게
    병존시키고 profile target으로 정확히 선택한다.
  - 공통 격자가 아닌 heatmap은 첫 Grad-CAM batch에서 예외가 발생한다.
  - 전체 관련 pytest가 통과한다.
- 전체 실험 완료 기준: EdgeFace의 LFW, SurvFace, RFW-Custom 새 run이 각각
  `COMPLETED`이며 phase/artifact manifest와 7×7 saliency shape가 일치해야 한다.

### 미해결 위험

- 더 이른 계층으로 이동하면 공간 세부 정보는 늘지만 최종 identity decision에
  대한 의미적 근접성은 낮아질 수 있다. faithfulness 및 stability 결과를 기존
  모델과 함께 보고 해석해야 한다.
- 7×7은 비교 가능한 격자를 제공할 뿐 backbone 간 receptive field와 channel
  semantics를 동일하게 만들지는 않는다.
- 전체 SurvFace Grad-CAM 비용은 그대로 크므로 실제 full run 완료 전에는 수정의
  데이터셋 전체 성공을 주장하지 않는다.

## 04:06 KST — 명시적 새 run이 이전 incomplete run을 보존하며 교체하도록 수정

- 작성일: 2026-08-10 04:06 KST
- 상태: 구현됨, 회귀 테스트 및 실제 plan resolution 검증됨

### 변경 배경

EdgeFace target을 7×7로 변경한 뒤 배치 노트북에서 `START_NEW_RUN=True`를
명시했지만, common runner가 이 플래그를 적용하기 전에 이전 3×3 SurvFace
incomplete run을 검사하여 `different incomplete dataset run is active`로
중단했다. 이 오류는 saliency 계산이 아니라 orchestration 제어 순서의 문제다.

### 결정 내용

- `START_NEW_RUN=False`에서는 기존과 동일하게 정확히 일치하는 incomplete run만
  재개하고, 다른 run은 fail-closed로 차단한다.
- `START_NEW_RUN=True`에서 active incomplete run의 config가 현재 plan과 다르면
  재개 대상으로 선택하지 않고 새 source/model freeze를 수행한다.
- active incomplete run이 이미 현재 plan과 정확히 일치하면 동일 run을 재개한다.
  따라서 새 7×7 run이 생성된 뒤의 Kernel Restart + Run All은 또 다른 run을 만들지
  않는다.
- 새 run 생성은 `RunStore.create`를 사용한다. 이전 run directory와 manifest,
  완료된 phase artifact는 삭제하거나 덮어쓰지 않는다.
- 새 run이 성공적으로 생성된 뒤에만 같은 dataset/date root의
  `active_run.json`이 새 run을 가리키므로, 이전 artifact는 보존하면서 이후 phase는
  새 7×7 run만 사용한다.

### 영향 범위와 재실행

- `research/experiments/pipeline_runner.py`: explicit-new-run 선택을 active-run
  mismatch 검사보다 먼저 적용한다.
- `research/experiments/step4_workflow.py`: source/model freeze에
  `start_new_run`을 전달하고 create/reuse 정책을 분리한다.
- `notebooks/common/orchestration/00_batch_experiment_runner.ipynb`의 기존
  `START_NEW_RUN=True` 설정을 그대로 사용할 수 있다.
- 커널을 재시작한 뒤 처음부터 실행하면 이전 3×3 run을 보존한 채 새 7×7 run이
  Phase 00부터 생성된다.

### 검증 기준 및 결과

- 서로 다른 incomplete config가 active여도 `start_new_run=True` resolution은
  현재 config와 `run=None`을 반환해야 한다.
- `start_new_run=False`의 기존 mismatch 차단 테스트는 유지되어야 한다.
- 관련 pipeline/workflow/run-store 테스트 36개가 통과했다.
- 실제 EdgeFace SurvFace full plan에서 이전 active run을 무시하고 현재 7×7 config를
  선택하는 것을 read-only resolution으로 확인했다.

### 미해결 위험

- 새 full run은 GPU 비용이 크므로 수정 검증 과정에서는 시작하지 않았다.
- 새 run 생성 전 Git clean 정책은 그대로 적용된다. 소스가 dirty이면 이전 run
  교체 전에 중단하므로 먼저 변경사항을 commit해야 한다.

## 04:31 KST — Windows manifest atomic replace의 일시적 잠금 재시도

- 작성일: 2026-08-10 04:31 KST
- 상태: 구현됨, 회귀 테스트 완료, 중단된 LFW run 재개 검증 대기

### 변경 배경

EdgeFace를 LFW와 RFW-Custom만 대상으로 다시 실행하는 과정에서 LFW Phase 00의
본문은 끝났지만, `phase_manifest.json`을 임시 파일에서 최종 파일로 교체하는
`os.replace()`가 `[WinError 5]`로 한 번 실패했다. 임시 manifest 작성에는
성공했으므로 디렉터리 권한 부재나 Git staging 문제가 아니라 Windows에서
백신·인덱서·Jupyter 등이 파일을 순간적으로 잡은 경우와 일치한다.

사용자가 정리한 이전 SurvFace run은 directory와 대용량 중간 artifact는 남아
있지만 핵심 `run_manifest.json`이 없어 `active_run.json`으로 열거나 검증할 수 없는
orphan 상태임을 별도로 확인했다. 현재 `DATASET_IDS=("lfw", "rfw_custom")`에는
SurvFace가 포함되지 않으므로 이번 LFW traceback의 원인은 아니다.

### 결정 내용

- `research.runtime.run_store._atomic_write_json()`은 임시 JSON을 먼저 완전히 쓴 뒤
  `os.replace()`의 `PermissionError`만 최대 8회 지수 backoff로 재시도한다.
- 지연은 0.05초부터 시작하며 총 대기 상한은 약 6.35초다.
- JSON serialization, 임시 파일 쓰기, 경로 오류 등 다른 예외는 재시도하지 않고
  기존처럼 즉시 실패한다.
- 마지막 replace도 실패하면 임시 파일을 보존해 traceback과 복구 근거를 남긴다.
- runtime 수정 commit으로 source snapshot이 바뀌므로, 현재
  `START_NEW_RUN=True` 실행은 기존 LFW R001을 덮어쓰지 않고 새 run을 Phase 00부터
  만든다. 실패한 R001/A001과 임시 manifest는 provenance로 보존한다.
- batch notebook의 dataset selector는 세 dataset 고정값이 아니라 명시적 subset을
  허용하는 계약으로 테스트한다.

### 영향 범위

- runtime: `research/runtime/run_store.py`
- tests: `tests/research/test_run_store.py`,
  `tests/research/test_notebook_layout.py`
- notebook: `notebooks/common/orchestration/00_batch_experiment_runner.ipynb`
- artifacts: 기존 LFW R001 run과 Phase 00 A001은 삭제하거나 수정하지 않는다.

### 검증 기준 및 재실행 범위

- 첫 두 번의 `os.replace()`가 `PermissionError`이고 세 번째가 성공하는 fixture에서
  최종 JSON, backoff 순서, 임시 파일 제거를 확인한다.
- run-store, pipeline, notebook contract 테스트가 통과해야 한다.
- 수정사항을 commit하고 커널을 재시작한 뒤 현재 2-dataset notebook을 처음부터
  실행하면 새 LFW run을 Phase 00부터 생성해야 한다. 실패 지점이 Phase 00
  manifest finalization이므로 LFW embedding/Grad-CAM의 고비용 결과는 유실되지
  않았다.
- 전체 GPU run은 자동으로 시작하지 않는다.

### 미해결 위험

- 다른 프로세스가 6.35초 이상 지속적으로 manifest를 잠그면 fail-closed로 다시
  중단한다. 이 경우 잠금 프로세스를 확인해야 하며 atomicity를 포기한 직접 덮어쓰기는
  허용하지 않는다.
- manifest가 삭제된 SurvFace artifact는 완전한 run으로 복구하거나 재사용하지
  않는다. 향후 SurvFace를 다시 실행하면 새 run을 명시적으로 생성해야 한다.

## 04:49 KST — Phase 05 다중 FPIR 조인 grain 복구

- 작성일: 2026-08-10 04:49 KST
- 상태: 구현됨, 단위·통합·실제 LFW artifact 검증됨, Phase 05 재실행 대기

### 변경 배경

EdgeFace LFW full run `20260810-R001-fa945179`은 Phase 00–04를 완료했지만,
Phase 05 retrieval-saliency 조인에서 모든 행이 두 개씩 중복으로 판정되어
중단되었다. `retrieval_metrics.csv`의 151,480행을 조사한 결과 같은
sample/profile/policy마다 `target_fpir=0.10`과 `0.01` 두 행이 존재했고, 두 행은
서로 다른 decision threshold와 accept/crossing 결과를 가진 정상적인 다중
operating-point 결과였다. Step7에서 다중 FPIR 산출을 추가했지만 Phase 05의
고유 키·통계 그룹·대표 사례 키에는 `target_fpir`가 전달되지 않은 것이 원인이다.
Git staging 삭제나 이전 run 종료는 이 오류의 원인이 아니다.

### 결정 내용과 데이터·모듈 흐름

- retrieval 행의 분석 grain을 `sample + model + compression profile + search mode +
  protocol/split + threshold policy + target_fpir`로 정의한다.
- `retrieval_metrics.csv` → streaming saliency join → association projection →
  saliency-retrieval association의 전 경로에서 `target_fpir`를 보존하고 그룹을
  분리한다. 두 FPIR 관측치를 같은 표본의 반복 측정으로 합치지 않는다.
- 대표 사례 선택도 FPIR별로 분리하고 tie key와 `case_id`에 `target_fpir`를 넣어
  서로 다른 operating point의 사례가 충돌하거나 소거되지 않게 한다.
- source correction으로 현재 Git snapshot이 frozen snapshot과 달라도, Phase 00–04
  완료와 정확한 Phase 05 join-grain 실패 및 retrieval column이 모두 확인되는 경우에만
  기존 run 재개를 허용한다. 이 제한된 복구 조건은 노트북에
  `START_NEW_RUN=True`가 남아 있어도 우선하며, 일반적인 다른 incomplete run은 기존
  explicit-new-run 정책을 유지한다.

### 현재 구현과 목표 구조의 차이

- 변경 전에는 다중 FPIR retrieval artifact가 정상 생성되었지만 downstream
  saliency 분석이 단일 FPIR를 가정했다.
- 변경 후에는 조인, association, 대표 사례의 모든 downstream grain이 다중 FPIR
  계약과 일치한다.
- 수치 Phase 05/06 산출물은 아직 재실행되지 않았으므로 구현·artifact 입력 검증과
  최종 분석 완료를 구분한다.

## 06:24 KST — multi-FPIR compact CSV round-trip tolerance 정합화

- 작성일: 2026-08-10 06:24 KST
- 상태: 구현됨, 실제 RFW-Custom PCA/PQ compact artifact 검증됨

### 변경 배경

RFW-Custom EdgeFace run `20260810-R001-49ce74ce`는 Phase 00–06과 immutable run
finalization을 모두 완료했다. 이후 `search_space_v4_multi_fpir` 파생 postprocessing의
PCA/PQ family artifact도 생성되었지만, 두 family를 병합하는 compact validation에서
`dir_rank1 compressed-minus-origin delta drifted`로 중단되었다.

실제 70개 retrieval compact row를 검사한 결과 PCA 4행, PQ 2행의
`delta - (compressed - origin)` 절댓값이 최대 약 `1.00008e-12`였다. compact CSV는
세 값을 각각 `%.12g`로 저장하므로 이 차이는 계산 drift가 아니라 독립적인 decimal
round-trip에서 가능한 오차다. 기존 절대 tolerance `1e-12`가 출력 계약보다 근소하게
작았다.

### 결정 내용과 데이터 흐름

- origin rate, compressed rate, stored delta의 compact CSV round-trip 일치 tolerance를
  `2e-12`로 정의한다. [0,1] rate를 12 significant digits로 각각 반올림할 때 가능한
  약 `1.5e-12` 상한을 포함하면서 그보다 큰 과학적 불일치는 계속 fail-closed로 막는다.
- raw score, count, denominator, Wilson interval, paired-bootstrap CI 또는 계산식을
  변경하지 않는다. tolerance는 compact serialization 이후의 일관성 검사에만 적용한다.
- `1.5e-12` round-trip 차이는 허용하고 `1e-6` 실제 delta drift는 거부하는 회귀 테스트를
  추가한다.

### 영향 범위와 재실행 범위

- 구현: `scripts/refresh_step4_search_spaces.py`
- tests: `tests/research/test_refresh_step4_search_spaces.py`
