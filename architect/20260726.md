## 2. 결정 내용

### 2.1 전체 노트북 책임 구조

```text
notebooks/
  prerequisite/
    datasets/       # manifest와 공통 aligned crop
    models/         # checkpoint 등록과 smoke
    embeddings/     # 원본 embedding 추출

    open_set/       # 검색·threshold·평가

      experiment/   # Pass B, 압축, 결합, 시각화
  reports/          # 완료 run 집계
  maintenance/      # guarded reset
```

노트북은 `research/`의 Python 함수를 호출하는 순차 runbook으로 한정한다.
모든 저장된 notebook code cell은 `execution_count=None`, `outputs=[]`,
`restart_kernel_and_run_all`을 유지한다.

### 2.2 실행 기본값과 fail-closed의 의미

일반 prerequisite·experiment·report에서 변수가 존재하면 다음을 기본으로 한다.

```text
DATA_FRACTION = 1.0
EXECUTE_STAGE = True
WRITE_OUTPUTS = True
OVERWRITE = True
```

이 변경은 입력 검증을 완화하지 않는다. checkpoint provenance, ModelSpec,
aligned bundle, hash, model UID 또는 lineage가 없거나 일치하지 않으면 즉시
중단한다. 즉 fail-closed는 “실행 플래그를 False로 두는 것”이 아니라
“검증되지 않은 입력으로 결과를 만들지 않는 것”으로 정의한다.

maintenance 노트북은 예외다. DB 연결, reset 실행, 완료/promoted override와
confirmation token은 계속 안전 기본값을 사용한다.

### 2.3 한 단계·한 run의 결과 계약

새 hash 폴더 규칙은 추가하지 않는다. 기존 `RunStore`의 다음 정보를 사용한다.

- KST 날짜와 순번을 가진 `run_id`
- canonical config hash
- 등록 입력 파일 hash
- phase attempt와 JSONL event log

같은 설정으로 첫 Grad-CAM prerequisite를 다시 실행하면 같은 미완료 active
run을 재사용한다. 같은 run의 단계별 canonical 파일은 staging 또는 원자적
파일 교체 후 하나만 남긴다. 다른 모델이나 다른 보정 config의 미완료 run을
자동으로 덮어쓰지 않는다.

마지막 대표 사례 결과까지 저장되면 run을 `COMPLETED`로 고정한다. 완료 run은
`OVERWRITE=True`여도 수정할 수 없다. open-set threshold나 보정 방법을 바꾼
반복 비교는 새 config hash와 새 run ID로 실행한다.

### 2.4 aligned crop

`research/preprocessing/aligned_crops.py`는 LFW manifest 전체에서 InsightFace
5-point ArcFace 정렬을 수행한다.

- 검출 실패를 center crop으로 대체하지 않는다.
- detection score, bbox area, 원래 순서로 얼굴 선택을 결정한다.
- 성공 결과가 하나도 없거나 geometry가 유효하지 않으면 중단한다.
- 완성된 replacement bundle을 staging한 뒤 canonical 폴더를 교체한다.

출력:

```text
data/interim/common/aligned_112/
  aligned_faces.npy
  aligned_index.csv
  failed_samples.csv
  bundle_manifest.json
  _SUCCESS
```

NPY는 모델 입력 배열이므로 유지하되 CSV index와 JSON checksum manifest를
반드시 동반한다.

### 2.5 PyTorch Step 2 압축 runner

`research/experiments/step2_compression.py`는 Pass A의 동일한 512D
`PreparedPopulationInputs`를 사용한다.

1. development split에서 PCA 384/256/128/64/32를 각각 독립 학습
2. development split에서 원본 512D PQ를 profile별 독립 학습
3. calibration split에서 origin threshold와 compressed threshold 선택
4. test open-set protocol에서 frozen-origin과 recalibrated-compressed 평가
5. paired geometry와 retrieval 결과에 origin embedding lineage 부착

PCA→PQ와 exact origin fallback은 허용하지 않는다. ONNX Step 1 artifact는
동일 checkpoint parity가 확인되지 않으면 이 runner 입력으로 사용하지 않는다.

### 2.6 저장 형식

| 데이터 종류 | canonical 형식 |
| --- | --- |
| 임베딩·압축 벡터·검색 상세 행 | PostgreSQL/pgvector |
| sample index·실패 목록·metric·집계표 | CSV |
| run/config/input lineage | JSON |
| 실행 event | JSONL 및 일반 log |
| embedding·heatmap dense array | NPY/NPZ + CSV index + JSON manifest |

완료된 과거 schema 1 Parquet artifact는 읽기 전용 호환을 유지하며 새로 쓰지
않는다.

## 6. 재실행 범위

1. 기존 완료 Step 1/Step 2 run은 읽기 전용으로 유지한다.
2. LFW source manifest나 정렬기 설정이 바뀌면 aligned crop을 다시 만들고 새

3. checkpoint, preprocessing, target layer 또는 선택 population이 바뀌면
   Grad-CAM prerequisite 00부터 새 run으로 실행한다.
4. Grad-CAM feature 정의만 바뀌면 같은 origin embedding을 재사용할 수 있는지
   lineage를 확인한 뒤 Pass B 이후를 새 run에서 실행한다.
5. PCA/PQ profile 또는 threshold 정책이 바뀌면 완료 run을 수정하지 않고 새
   config의 run에서 압축 단계 이후를 실행한다.
6. 보고 노트북은 완료 run을 읽기 전용으로 집계한다.

## 7. 검증 기준과 현재 결과

- 일반 실험의 full/execute/write/overwrite 기본값
- maintenance의 DB/reset/override/token 안전 기본값
- aligned crop의 missing/no-face/index/hash/atomic replacement

- 동일 미완료 RunStore 재사용, 다른 미완료 config 덮어쓰기 거부

- PCA-only/PQ-only, fallback-free, strict origin lineage
- 과거 schema 1 Parquet artifact 읽기 호환

현재 검증은 단위·synthetic와 notebook 정적 수준이다. 실제 공개 checkpoint,
전체 LFW aligned crop, 전체 Grad-CAM GPU 실행과 PostgreSQL 결과는 아직
검증되지 않았다.

## 8. 미해결 위험

1. **전체 기본 실행 비용**
   - 기본값이 full/execute이므로 prerequisite가 준비된 환경에서 Run All은 즉시
     장시간 GPU 작업을 시작한다.
   - GTX 1080 Ti의 모델별 batch/OOM/소요 시간을 첫 실제 run에서 기록해야 한다.

2. **실제 detector와 crop 재현성**
   - InsightFace 모델 패키지 버전과 detector weight provenance를 bundle manifest
     밖의 환경 manifest와 함께 고정해야 한다.

3. **여러 모델 완료 run 비교**
   - active run은 한 번에 하나만 허용한다.
   - ArcFace run을 완료한 뒤 AdaFace와 MagFace를 각각 새 run으로 실행하고,
     reports 단계에서 세 완료 run을 명시적으로 선택해야 한다.

4. **CSV 크기와 정밀도**
   - scalar/index table은 CSV가 해석 가능하지만 대규모 dense embedding 자체를
     CSV로 저장하면 크기와 정밀도 문제가 생긴다.
   - dense vector는 DB 또는 NPY/NPZ에 두고 CSV에는 key·index·metric만 둔다.

5. **과거 Parquet 호환 경계**
   - schema 1 reader는 완료 artifact 재사용만을 위한 것이다.
   - 과거와 현재 결과를 합칠 때 dtype과 schema version을 manifest로 확인해야 한다.

6. **open-set 반복 실험**
   - 보정 수정마다 새 run이 생기므로 reports에서 기준/후보 run의 역할을
     명시하지 않으면 cherry-picking 위험이 있다.
   - target FPIR, threshold source split과 config hash를 표에 포함해야 한다.

2. 새 경로에서 실행할 때는 해당 데이터셋 README의 첫 단계부터 시작한다.
3. 노트북 내부 상태에 의존하지 않고 커널 재시작 후 위에서 아래로 실행한다.
4. 기존 자동화나 개인 실행 스크립트가 옛 경로를 참조하면 새 경로로 갱신한다.
5. 입력 hash나 config가 바뀐 경우에만 기존 lineage 규칙에 따라 새 run을 만든다.

## 7. 검증 기준

- 모든 `.ipynb`가 정확히 하나의 데이터셋 또는 `common` 아래에 존재
- LFW/SurvFace는 단계 폴더가 숫자 순서로 연결
- RFW/BalancedFace의 제한된 연구 역할이 유지
- 기존 `notebooks/prerequisite`, `notebooks/experiments`,
  `notebooks/reports`, `notebooks/maintenance` 활성 참조 0건
- notebook JSON/schema, 코드 셀 compile, 빈 output, restart policy 유지
- 일반 실행 기본값과 maintenance 안전 기본값 유지
- 관련 단위 테스트와 전체 테스트 통과

현재 검증 결과:

- 노트북 관련 테스트: 23개 통과
- 전체 테스트: 245개 통과
- 활성 문서의 노트북 경로 참조 26개 검사, 누락 0개
- 이전 책임별 활성 경로 참조 0개
- Ruff와 `git diff --check` 통과
- 실제 데이터셋 전체 Run All과 GPU 실험은 실행하지 않음

## 8. 미해결 위험

1. 외부 개인 스크립트나 Jupyter 최근 파일 목록은 Git 검색으로 확인할 수 없다.
2. LFW의 `03_open_set`은 과거 fallback 재현 경로도 포함하므로 현재 Step 1
   fallback-free 특성화와 혼동하지 않아야 한다.
3. RFW와 BalancedFace에 아직 없는 실험 폴더를 미리 만들면 구현 상태를
   과장할 수 있으므로 실제 단계가 생길 때 추가한다.
4. 기본값이 full execution이므로 새 경로에서 무심코 Run All하면 장시간 작업이
   시작될 수 있다는 기존 위험은 그대로 남는다.
